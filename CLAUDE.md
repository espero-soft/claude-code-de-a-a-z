## Contexte

Projet fil rouge de la formation « Claude Code de A à Z » : application de réservation de salles d'un centre d'affaires (Next.js App Router, Prisma + SQLite, Tailwind). Code, identifiants, commentaires et textes d'interface sont **en français** ; garder cette convention.

Versions figées dans `package.json` (Next 16, React 19, Prisma 7, Tailwind 4) pour rester identique aux vidéos : ne pas les mettre à jour. Les tags `fin-module-XX` marquent l'état du projet à la fin de chaque module.

## Règles métier (cahier des charges)

Texte exact du cahier des charges ; le code y renvoie par leur numéro (« R1 »...).

| Règle | Texte | Codée ? |
|---|---|---|
| R1 | Une réservation dure au minimum 1 heure, par tranches de 30 minutes. | Oui : `validerReservation` (`src/lib/reservation.ts`) |
| R2 | Le centre est ouvert du lundi au vendredi, de 8 h à 20 h. | Oui : `validerReservation` (`src/lib/reservation.ts`) |
| R3 | Deux réservations confirmées ne peuvent pas se chevaucher sur la même salle. | Oui : `conflitConfirme` (`src/lib/chevauchement.ts`) et la requête partagée `trouverConflitConfirme` (`src/lib/conflit-confirme.ts`), appelée dans `reserver` (`actions.ts`), avant d'ouvrir le paiement (`ouvrirPaiement`) et dans la transaction de `confirmerReservation` (`src/lib/confirmation.ts`), lancée après un paiement vérifié. Seules les `CONFIRMEE` bloquent un créneau ; un paiement arrivé sur un créneau pris entre-temps est remboursé. |
| R4 | On ne peut pas réserver dans le passé. | Oui : `validerReservation` (`src/lib/reservation.ts`) |
| R5 | Le montant = prix par heure x durée. | Oui : `calculerMontant` (`src/lib/montant.ts`), appelé dans `reserver` (`actions.ts`) ; Stripe Checkout encaisse ce montant relu en base, et `decisionPaiement` vérifie le montant payé. |
| R6 | Une réservation en attente de paiement depuis plus de 15 minutes est annulée automatiquement. | Oui, **à la consultation et au paiement** (pas de tâche planifiée) : `estExpiree` (`src/lib/expiration.ts`), `decisionPaiement` (`src/lib/paiement.ts`), appliquée par `actualiserReservation` (`src/lib/suivi-paiement.ts`). Une réservation jamais consultée reste `EN_ATTENTE` en base, mais ne bloque rien (seules les `CONFIRMEE` comptent pour R3). |

## Architecture

- **Logique métier pure dans `src/lib/`**, testée à côté (`*.test.ts`) sans base ni Next. `validerReservation(saisie, maintenant)` renvoie `{ ok: true, ... } | { ok: false, erreurs }` (un message par champ) ; `maintenant` est injecté pour des tests déterministes.
- Toutes les heures sont celles du centre, **Europe/Paris** (`FUSEAU_CENTRE`), quel que soit le fuseau du serveur : passer par `heureDeParis` pour convertir une saisie, et `FUSEAU_CENTRE` pour tout affichage de date.
- **Montants en centimes entiers** partout (base et calculs) ; division par 100 seulement à l'affichage. Le prix vient toujours de la base, jamais du formulaire.
- **Flux de réservation** : `salles/[id]/reserver/FormulaireReservation.tsx` (client, `useActionState`) appelle la Server Action `actions.ts` (`reserver`, liée au `salleId` par `bind`). Elle valide, renvoie `{ erreurs, valeurs }` en cas d'échec (pour ne pas vider le formulaire), sinon crée la réservation `EN_ATTENTE` rattachée au compte connecté (`Reservation.utilisateurId`, son titulaire) et redirige vers `/reservations/[id]`. Réserver exige un compte (page et action). **Le nom et l'e-mail viennent du compte**, jamais du formulaire (plus de champ e-mail ; l'action ignore ceux d'un formulaire forgé). Un compte encore sans nom (créé par le code) le saisit une fois : il est enregistré dans `user.name` et n'est plus demandé.
- **Paiement (Stripe Checkout, mode test, sans webhook)** : la page `/reservations/[id]` d'une réservation `EN_ATTENTE` affiche le bouton « Payer » (`BoutonPayer.tsx`, `useActionState`) qui appelle la Server Action `payer` (`reservations/[id]/actions.ts`), puis `ouvrirPaiement` (`src/lib/suivi-paiement.ts`) : R6 et R3 vérifiées, session Checkout créée au montant de la base (`client_reference_id` = id de la réservation), son id enregistré dans `Reservation.stripeSessionId`, redirection vers Stripe. Stripe renvoie sur `/reservations/[id]` ; à chaque consultation, `actualiserReservation` relit la session **auprès de Stripe** (rien du navigateur n'est cru) et applique `decisionPaiement` (fonction pure, `src/lib/paiement.ts`) : confirmer via `confirmerReservation`, annuler (R6, en fermant d'abord la session ouverte) ou rembourser puis annuler (paiement encaissé après 15 min, mauvais montant, créneau pris). Le délai R6 d'un paiement se mesure à l'encaissement (date de la charge), pas au retour du client. Clé `STRIPE_SECRET_KEY` (test uniquement, `sk_test_…`) lue par `obtenirStripe` (`src/lib/stripe.ts`) ; carte de test `4242 4242 4242 4242`. SDK `stripe` 23 : `allowed_payment_method_types` remplace `payment_method_types`.
- **Cache Components activé** (`cacheComponents: true` dans `next.config.ts`) : les pages dynamiques gardent une coquille statique et placent la lecture des données dans un composant enfant sous `<Suspense>`, qui commence par `await connection()`. `params` est une promesse, résolue via `params.then(...)` dans le Suspense ; typer avec `PageProps<"/route/[id]">`. `react.cache()` évite les doubles lectures entre `generateMetadata` et la page.
- **Rôles et accès (module 12)** : `CLIENT` (défaut), `EMPLOYE` (réservations et tickets, ni chiffres, ni comptes, ni journal), `ADMIN` (tout). Rôle stocké dans `user.role` (champ `additionalFields` de Better Auth, `input: false` : jamais modifiable depuis le navigateur). Règles **pures et testées** dans `src/lib/roles.ts` (`peut(role, capacite)`, `peutVoirReservation`, `peutPayerReservation`, refus par défaut) ; lecture de session et du rôle **en base** dans `src/lib/acces.ts` (`lireUtilisateur`, `utilisateurAvec("tickets")`, `react.cache`). **Chaque Server Action revérifie elle-même session et rôle** (tests `src/app/**/actions.test.ts`, qui les appellent directement) ; chaque page aussi, sous `<Suspense>`. `/reservations/[id]` : titulaire, employé ou admin ; pour les autres, `notFound()`, exactement comme une réservation inexistante, et le contrôle se fait **avant** `actualiserReservation` (qui écrit). Ce contrôle (`exigerAccesReservation`, `react.cache`) est appelé aussi par `generateMetadata` : le titre de l'onglet est décidé par le serveur après le contrôle, jamais un titre statique qui partirait dans la coquille et trahirait l'existence de la réservation. Page introuvable générale en français : `src/app/not-found.tsx` (titre `TITRE_INTROUVABLE`, composant `Introuvable`). Seul le titulaire paie. Liens réservés aux comptes connectés (`LIEN_ESPACE_CLIENT` « Mes réservations » pour tous, `LIEN_ADMINISTRATION` « Tickets » pour le personnel, `LIEN_JOURNAL` « Journal » pour l'administrateur), dans `liens-navigation.ts` mais **hors du tableau `LIENS`** (public) : ajoutés à l'en-tête par `ZoneCompte`, disposition `liens`. Premier admin : `npm run admin:creer` (`scripts/creer-admin.ts`, adresse en argument, jamais dans le code).
- **Espace client `/compte` (module 12)** : réservations du compte connecté (filtre `utilisateurId`), rangées par `classerReservations` en en attente / à venir / passées et annulées, actions par statut via `actionsReservation` (`src/lib/espace-client.ts`, pur et testé : jamais « Payer » sur une confirmée). Les `EN_ATTENTE` sont actualisées (`actualiserReservation`) avant l'affichage. Seul bouton cuivre : « Réserver une salle » ; « Payer » y est marine (`BoutonPayer variante="principal"`).
- **Rattachement des réservations faites sans compte** (`src/lib/rattachement.ts`) : `utilisateurId` vide et même e-mail (casse et espaces ignorés) → rattachée au compte, **seulement si `emailVerified`**, jamais si elle a déjà un titulaire (revérifié à l'écriture). Lancé à chaque connexion (`databaseHooks.session.create.after` dans `src/lib/auth.ts`, sans jamais faire échouer la connexion) et à l'ouverture de `/compte`.
- **Mon profil `/profil` (SECURITE.md section 14)** : nom (`validerNom`), appareils connectés = sessions valables (`listerAppareils`, `decrireAppareil`, purs dans `src/lib/profil.ts` ; seul l'identifiant de session part vers le navigateur, jamais le jeton ; `lireUtilisateur` renvoie `sessionId`), déconnexion d'un appareil (filtrée sur `userId`, jamais la session courante) ou de tous les autres. **Suppression du compte** : nouveau code e-mail (table `CodeSuppressionCompte` : empreinte, 5 min, 3 essais, même session), second facteur exigé du personnel, dernier administrateur refusé (rôle **enregistré**, revérifié dans la transaction), paiements Stripe en cours fermés d'abord (`fermerPaiementsEnCours`, sinon refus), puis `effacerCompte(client, id)` (`src/lib/suppression-compte.ts`, testé sur une vraie base SQLite temporaire) : réservations payées ou passées par Stripe gardées **anonymisées** (« Client supprimé », e-mail vide, sans titulaire), les autres, tickets, codes et compteurs supprimés, compte supprimé (cascade). Puis `/compte-supprime`. Lien : l'initiale du compte sur ordinateur (`LienInitiale`), « Mon profil » dans le menu mobile (`LIEN_PROFIL`, `seulementMobile`). Bouton `variante="danger"` pour l'irréversible.
- **Journal des connexions `/admin/journal` (SECURITE.md section 15)** : réservé à l'**administrateur** (capacité `journal`, pas l'employé). Table `EvenementConnexion` (type, e-mail en minuscules, compte, motif, IP, navigateur), sans relation vers `user` (la trace d'un compte supprimé reste). **Jamais un code, un jeton ni un secret** : aucun champ libre, type et motif dans des listes fermées (`TYPES_EVENEMENT`, `MOTIFS`), `preparerEvenement` ne garde que les champs prévus, nettoyés (`src/lib/journal.ts`, pur). Écriture par `journaliser(client, evenement)` (`src/lib/journal-connexions.ts`), qui ne fait jamais échouer l'opération et **efface ce qui a plus de 90 jours** à chaque écriture ; `lireJournal` purge aussi avant de lire, filtre par sous-chaîne d'e-mail avec `instr()` (le `contains` de Prisma laisse `%` et `_` agir en jokers sous SQLite), 200 lignes au plus. Branchement : crochets `journalConnexions` (`src/lib/garde-journal.ts`, `noterEvenement` y ajoute IP et navigateur) pour code demandé, connexion réussie, code refusé, second facteur validé ou refusé et déconnexion. Un refus levé par un crochet `before` empêche les crochets `after` de passer : `gardeConnexion` et `gardeDeuxiemeFacteur` journalisent donc elles-mêmes « compte bloqué » et le rejeu d'un code TOTP. Les actions de `/profil` journalisent appareil déconnecté et compte supprimé. Tests : `journal.test.ts` (pur), `journal-connexions.test.ts` (vraie base temporaire), `journal-auth.test.ts` (vrai Better Auth sur base temporaire : aucun code en base), `e2e/admin-journal.spec.ts`. Après une migration, **redémarrer `npm run dev`** : le client Prisma gardé sur `globalThis` ne connaît pas les nouvelles tables.
- **Second facteur du personnel (TOTP, SECURITE.md section 13)** : obligatoire pour `EMPLOYE` et `ADMIN`. Le module `twoFactor` de Better Auth ne s'enclenche qu'après un mot de passe : il sert seulement à créer le secret et les 10 codes de secours (chiffrés, table `twoFactor`) et à vérifier un code. La session ouverte par le code e-mail est **marquée** (`Session.deuxiemeFacteurLe`, valable 12 h et pour cette session seulement) par `gardeDeuxiemeFacteur` (`src/lib/garde-deuxieme-facteur.ts`, crochets Better Auth). Cette garde réserve `/two-factor/*` au personnel, ferme en 404 `get-totp-uri`, `disable`, `generate-backup-codes`, `send-otp` et `verify-otp` (la seule session e-mail suffirait sinon), limite à 5 essais par heure et par compte, et refuse un code déjà servi (table `CodeDeuxiemeFacteurUtilise`). **Rôle effectif** : `lireUtilisateur` renvoie dans `role` le rôle ramené à `CLIENT` tant que la session n'est pas marquée (`roleEffectif`, `etatDeuxiemeFacteur`, purs dans `roles.ts`) ; tous les contrôles lisent `role`. `roleCompte` et `deuxiemeFacteur` ne servent qu'à guider (`doitValiderDeuxiemeFacteur`, `adresseDeuxiemeFacteur`) et à afficher « Tickets », **jamais à ouvrir un droit**. Écran `/double-authentification` : enrôlement guidé (QR code `uqr`, clé et codes de secours affichés une seule fois), puis un code à chaque session ; Server Actions `commencerEnrolement` et `validerCode` (par `auth.api`). Tests e2e sans téléphone : `e2e/totp.ts` calcule le code (RFC 6238, `node:crypto`) ; `seConnecterPersonnel` (`e2e/session.ts`) connecte un employé ou un admin avec son second facteur.
- **Proxy (`src/proxy.ts`)** : contrôle **optimiste** seulement, jamais une barrière. Visiteur sans cookie de session sur `/salles/:id/reserver`, `/reservations/:id`, `/compte`, `/profil`, `/double-authentification` ou `/admin/**` : redirection vers `/connexion?retour=...` (`adresseConnexion`). Sur `/admin/**`, relit aussi le rôle pour qu'un client reçoive un vrai 404 (réécriture vers `/admin/introuvable`), et renvoie le personnel sans second facteur validé vers `/double-authentification?retour=...`. Puis la capacité exigée par la page (`capacitePageAdmin` dans `roles.ts` : `tickets`, `journal`, et `comptes` par défaut pour une page inconnue) : 404 aussi pour l'employé sur `/admin/journal`. Toute nouvelle page de `/admin` ou réservée aux comptes : l'ajouter au `matcher` (et à `capacitePageAdmin` pour `/admin`) ET la protéger dans la page et ses actions.
- **404 des salles** : la fiche est envoyée en flux, donc son code HTTP ne peut plus changer après coup. `src/proxy.ts` (le « middleware » de Next 16) vérifie la salle avant le rendu sur `/salles/:id` et `/salles/:id/reserver`, et réécrit vers `/salles/introuvable`, page statique qui appelle `notFound()` et affiche `salles/not-found.tsx`. Ajouter toute nouvelle route sous `/salles/[id]` au `matcher` du proxy si elle doit répondre un vrai 404. Le matcher exclut les segments contenant un point (`:id([^/.]+)`), sinon les photos de `public/salles/*.jpg` seraient prises pour des salles inconnues.
- **Photos des salles** : `public/salles/<slug>.jpg` (1600 px de large, tirées de `design/photos/`), chemin dans `Salle.photo` (seed), affichées par `PhotoSalle` (`next/image`, toujours avec `sizes` ; aplat avec monogramme si `photo` est vide). `next.config.ts` (`images.localPatterns`) n'optimise que `/salles/**`.
- Une salle avec `active: false` est traitée comme inexistante (filtre `active: true` dans chaque requête).
- **Production (`design/PLAN-PRODUCTION.md`, `deploiement/`, `scripts/production/`)** : VPS Ubuntu, `next start -H localhost -p 3000` sous systemd derrière Caddy, SQLite dans `/var/lib/reunea`, secrets dans `/etc/reunea/reunea.env` lié en `.env`. **Jamais `-H 127.0.0.1`** : Next 16.4.5 envoie alors les réécritures du proxy (404 des salles, de `/admin`) vers `localhost` comme vers un site extérieur, et elles échouent. Configuration lue par `src/lib/configuration.ts` (pur, testé) : `adressePublique` (`BETTER_AUTH_URL`, aussi l'adresse de retour Stripe, jamais l'en-tête `Origin`), `optionsSmtp` (Mailpit sans TLS ; ailleurs STARTTLS **exigé**, ou TLS implicite sur 465 ; `SMTP_TLS` pour forcer), `reservationDemoAutorisee` (le seed n'insère pas la réservation de démonstration avec `NODE_ENV=production` ou une adresse https), `verifierConfiguration`. `src/instrumentation.ts` refuse de démarrer une production mal configurée (`process.exit(1)` par `src/lib/demarrage-node.ts` : une exception laisserait Next en vie à répondre 500), jamais pendant le build (`NEXT_PHASE`). `/api/sante` (`SELECT 1`, `connection()`, `no-store`) sert au contrôle de fumée (`fumee.sh`, lecture seule), qui décide du retour automatique de `deployer.sh`. Identifiant de déploiement par `NEXT_DEPLOYMENT_ID` au build (pas dans `next.config.ts`). **Livraison depuis la branche du module** (`deployer.sh <étiquette> <branche>`, branche `main` ou `module-<n>`) : `main` reste vierge pour les apprenants, on n'y fusionne jamais. L'étiquette doit exister sur GitHub (`ls-remote`, pas le clone du serveur), être annotée, et son commit être sur la branche telle qu'elle est sur GitHub. Le clone du serveur part de la branche du module (`git clone --branch`), sinon le premier `deployer.sh` n'existe pas. Migrations : on ajoute, on ne supprime qu'une livraison plus tard (retour arrière du code sans toucher la base). Site de **démonstration** : `BandeauDemonstration` sur chaque page (`layout.tsx`) et page `/demonstration` (lien « Démonstration » dans `LIENS`). **Remise à zéro chaque nuit** (2 h 30, Paris, `deploiement/reunea-remise-a-zero.timer`, après une sauvegarde) : `remettreAZeroDemo` (`src/lib/remise-a-zero-demo.ts`, testé sur vraie base) efface toutes les réservations et les comptes `CLIENT` (ou sans rôle) avec leurs codes, compteurs et tickets ; jamais les salles, `EMPLOYE`/`ADMIN` ni le journal. `poweredByHeader: false` (`next.config.ts`), vérifié par `fumee.sh` ; chaque version est contrôlée par **son propre** `fumee.sh` (`fumee_de`, `commun.sh`), au retour arrière aussi. **Fausses clés des tests** (Stripe, Anthropic) : toujours `cleStripeFactice` / `cleAnthropicFactice` (`src/lib/cles-factices.ts`), jamais une clé écrite d'un seul tenant (protection de push de GitHub) ; `cles-factices.test.ts` scrute tout le dépôt. Tests des scripts : `scripts/production/production.test.ts` (vrais bash, git, sqlite3 et HTTP dans un dossier temporaire ; faux systemctl et npm).
- **Design (charte Réunéa, `design/charte.md`)** : jetons de `design/tokens.json` en variables `@theme` dans `globals.css` (`bg-marine`, `text-cuivre`, `font-titres`, `text-titre-1`, `rounded-arrondi-m`, `shadow-carte`...), polices Playfair Display et Manrope par `next/font` dans `layout.tsx`. ## Sécurité

Permissions définies dans `.claude/settings.json` (partagé via git, donc valables pour tout le monde). Ordre d'évaluation : `deny` l'emporte sur `ask`, qui l'emporte sur `allow`.

- **Autorisé sans confirmation** : `npm run lint`, `npm test`, `npx vitest` (avec ou sans arguments), `git status`, `git diff`, `git log` (lecture seule).
- **Toujours refusé** : le push forcé, `rm -rf` et `rm -fr`, la lecture de `.env` (secrets ; s'appuyer sur `.env.example`), l'écriture dans la base par le serveur MCP `sqlite`.
- **Confirmation demandée** : tout autre `git push`, `git reset --hard`, `git tag` (une étiquette annotée poussée est livrable), et tout ce qui touche le serveur : `ssh`, `scp`, `rsync`, `sftp`, `sudo`, les scripts de `scripts/production/`.

Les règles de permission comparent des motifs de commande : une autre écriture peut leur échapper. Les cas graves sont donc aussi bloqués par des hooks `PreToolUse` qui découpent la commande comme le shell (ordre des mots, `bash -c`, `eval`, `$(…)`) : `proteger-push.mjs` (push forcé : `--force`, `--force-with-lease`, `-f` même groupé comme `-uf`, `--mirror`, `+branche`), `proteger-base.mjs` (remise à zéro de `dev.db`), `proteger-migrations.sh` (migration existante). `rm -r -f` reste seulement couvert par le motif. Ne pas chercher à contourner une règle ; demander à l'utilisateur.

**Branche `main` sur GitHub (SECURITE.md section 16)** : protégée par deux rulesets versionnés dans `.github/rulesets/` : ni forçage ni suppression (aucun contournement, administrateur compris) ; PR obligatoire avec 1 approbation humaine et le contrôle « Lint et tests » au vert (`.github/workflows/verifications.yml`, ne pas renommer le job), contournable seulement par l'administrateur du dépôt en fusionnant une PR. Ne jamais pousser sur `main` : passer par une branche et une PR. `claude-pr.yml` refuse une PR dont la branche source est `main`. Appliquer : `bash scripts/proteger-main.sh` ; prouver, en lecture seule : `bash scripts/verifier-protection-main.sh`.

Réglages personnels : `.claude/settings.local.json` et `CLAUDE.local.md` (ignorés par git). Guide pour les nouveaux venus : `CLAUDE-CODE-EQUIPE.md`.
